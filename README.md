# proxy_tg

Личный MTProto-прокси для Telegram на VPS в Амстердаме (`178.62.199.241`).
Маршрут: приложение Telegram → VPS → Telegram. Сам Telegram-бот продолжает
работать отдельным сервисом. Прокси не требует токена бота или входа в аккаунт.

Используется официальный [TelegramMessenger/MTProxy](https://github.com/TelegramMessenger/MTProxy),
версия зафиксирована в `UPSTREAM_REVISION`. Развёртывание и первый запуск управляются GitHub Actions.

## Структура

- `proxy.py` — проверка настроек, запуск, ссылка подключения, обновление конфигурации Telegram;
- `probe.py` — реальный MTProto handshake без авторизации в аккаунт;
- `deploy/` — сборка, установка, применение релиза и systemd;
- `tests/` — проверки конфигурации, защиты секрета и отказов обновления;
- `.github/workflows/pipeline.yml` — тесты, сборка Linux-бинарника и управляемая выкладка.

## Локальная подготовка

Python 3.9+; проверки не требуют сторонних библиотек и не обращаются в сеть:

```bash
make check
cp .env.example .env
# Заполнить PROXY_SECRET: 32 случайных шестнадцатеричных символа.
python3 proxy.py --env-file .env validate
```

`make build` предназначен для Linux с GCC, make, OpenSSL и zlib.
На macOS используйте сборку GitHub Actions. На VPS компилятор не нужен:
Actions собирает бинарник на Ubuntu 24.04 для Ubuntu 24.04+ x86_64.

## CI и автодеплой

Каждый push в `main` и pull request запускает тесты, проверку shell-сценариев,
сборку официального MTProxy и проверку systemd units. Результат сохраняется
как GitHub Actions artifact.

Deploy job выключен, пока repository variable `AUTO_DEPLOY_ENABLED` не равна `true`.
Нужны secrets:

- `VPS_HOST` — `178.62.199.241`;
- `VPS_USER` — административный пользователь (сценарии требуют root);
- `DEPLOY_KEY` — отдельный ключ для этого репозитория;
- `VPS_FINGERPRINT` — проверенный SHA256 fingerprint SSH-хоста VPS.

Публичный ключ деплоя должен быть установлен на VPS. Никакие реальные ключи,
секреты прокси и ссылки подключения в Git не добавляются. Репозиторий публичный.

Первый deploy создаёт `/etc/proxy_tg/proxy.env` с новым случайным секретом,
пользователя `proxy-tg`, конфигурацию Telegram и release в `/opt/proxy_tg/releases/` с SHA коммита и номером попытки выкладки.
Уже существующий секрет не перезаписывается. Атомарная ссылка `current`
выбирает release. Настройки и конфигурация Telegram находятся вне release.

**Без `/opt/proxy_tg/.allow-deploy-start` сервис остаётся выключенным.**
Для первого включения после проверки подготовленного релиза владелец разрешает
создание marker-файла и повторный deploy. Для подключения должен быть доступен
TCP-порт `PROXY_PORT` (по умолчанию 443), включая firewall провайдера.

## Ресурсы и обслуживание

Прокси работает от отдельного непривилегированного пользователя с правом
открывать порт 443. Один worker, буферы 16 МиБ, не более 64 клиентских соединений
на worker. Systemd ограничивает память до 128 МиБ и CPU до 50% одного ядра.
Это настройки для личного использования на VPS с 512 МБ RAM.

Конфигурация Telegram скачивается по HTTPS ежедневно. Обе части загружаются
до замены, затем переключаются одной ссылкой. При ошибке остаётся прежняя пара.
После успешного обновления активный прокси перезапускается; возможен короткий
перерыв соединения. Хранятся текущая и предыдущая конфигурации.

Проверка деплоя использует локальный TCP-порт прокси и стабильность сервиса.
Параметр STATS_PORT задаёт внутренний идентификатор MTProxy; отдельный HTTP endpoint
статистики не включается, чтобы не открывать дополнительный сетевой порт.
При неуспешной активации восстанавливается предыдущий release. При первой
неудачной активации сервис останавливается. Изменения конфигурации и схемы
systemd перед выкладкой также требуют проверки.

```bash
systemctl status proxy-tg.service proxy-tg-refresh.timer --no-pager
journalctl -u proxy-tg.service -n 50 --no-pager
systemctl show proxy-tg.service -p MemoryCurrent -p NRestarts
```

## Подключение и проверка

Ссылка содержит секрет доступа. Получить её на VPS, не публикуя в журнале CI:

```bash
python3 /opt/proxy_tg/current/proxy.py --env-file /etc/proxy_tg/proxy.env link
```

Ссылка добавляет `dd` к секрету для транспорта со случайным padding.
Откройте её в приложении Telegram и включите прокси. Это прокси для Telegram,
а не VPN для всего устройства. Работоспособность зависит также от доступности
VPS из сети пользователя.

Для независимого end-to-end теста:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements-check.txt
.venv/bin/python probe.py --env-file .env
```

Тест получает ответ Telegram через прокси без входа в аккаунт. Локальная TCP-
проверка сама по себе не подтверждает обмен с Telegram, поэтому первый запуск
следует дополнительно проверить этой командой и приложением на телефоне.

## Первоначальная подготовка

3 ноября 2026 года на VPS уже установлены зависимости и отдельно собран MTProxy
в `/opt/mtproxy/` при предварительной подготовке. Этот каталог не управляется
данным проектом. Штатные release этого проекта находятся в `/opt/proxy_tg/`. Telegram-бот и monitoring работают
независимо. Старую сборку можно убрать после успешного перехода на проект.

## Fake TLS для фильтруемых сетей

`PROXY_TLS_DOMAIN=www.google.com` в `/etc/proxy_tg/proxy.env` включает
TLS-эмуляцию официального MTProxy. Ссылка меняется на `ee` + секрет + домен в hex.
Требуется заменить секрет в настройках Telegram на выданный командой `link`.
Старый `dd`-секрет в этом режиме не подключается. Базовый секрет доступа не меняется.
Процесс запускается без дополнительных fork-worker согласно рекомендации upstream.
`probe.py` проверяет HMAC сервера и реальный ответ Telegram также в Fake TLS режиме.
Это не гарантирует доступность при блокировке самого IP VPS или сети по белому списку.

## Резервный порт

`PROXY_ALT_PORT=8443` включает второй listener с тем же секретом и доменом,
не отключая основной 443. Получить ссылку: `proxy.py --env-file /etc/proxy_tg/proxy.env link --port 8443`.
Резервный порт тоже должен быть доступен через сеть и firewall провайдера.
При диагностике iPhone через МегаФон на 443 наблюдались неполные ClientHello:
1327 полученных байт вместо объявленных 1520–1537. Это наблюдение на входе VPS,
а не доказательство конкретного оборудования или оператора, теряющего пакеты.

## Личный SOCKS5 параллельно с MTProxy

Отдельный `proxy-socks.service` (Dante из Ubuntu) слушает TCP8443. MTProxy443,
его секрет и конфигурация не изменяются и не перезапускаются этой выкладкой.
Логин `tgproxy`, пароль создаётся один раз случайно (192 бита), хранится только
в `/etc/proxy_tg/socks-credentials.json` с правами600. Пользователь без shell-доступа.

Обязательна SOCKS5 username/password авторизация; анонимный доступ и неверный
пароль отклоняются. Разрешён только TCP CONNECT к официальным IPv4-сетям Telegram
из https://core.telegram.org/resources/cidr.txt; SOCKS4, UDP, BIND и сторонние
назначения не разрешены. Пароль не используется для других сервисов. SOCKS5
username/password не шифрует сам пароль на сетевом пути; Telegram дополнительно
шифрует свой трафик. Это не VPN для всего устройства.

MSS1024 применяется только к исходящим SYN-ACK порта8443 через отдельный
`proxy-socks-mss.service`, который автоматически запускается перед Dante после
перезагрузки. Правило не открывает доступ и не затрагивает порт443.
Значение1024 — проверяемая настройка SOCKS5, а не подтверждённый ранее ремонт MTProxy.

Автодеплой SOCKS5 отдельный: `.github/workflows/socks.yml`, variable
`SOCKS_DEPLOY_ENABLED=true`. Изменения socks/ не запускают выкладку MTProxy.
Проверка внешнего подключения (пароль передаётся только в память):

```bash
# Запускать из изолированного окружения с requirements-check.txt.
ssh root@178.62.199.241 'cat /etc/proxy_tg/socks-credentials.json' | \
  .venv/bin/python socks/probe.py --credentials-file /dev/stdin
```

Проверяются отсутствие анонимного доступа, неверный пароль, TCP MSS, ограничение
назначений и полноценный обмен ключами MTProto с Telegram. В отчёте пароль скрыт.
Сервис имеет Restart=on-failure, автозапуск, MemoryMax128M и CPUQuota25%.
